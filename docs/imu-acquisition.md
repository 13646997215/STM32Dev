# GY953持续采集与停更诊断（2026-10-19）

## 结论与证据边界

用户实测：独立CH340通信稳定；集成接线后姿态停更，再点击旧Euler开关可恢复。此前被动旁听时原始输出也停止，不能单独归因到STM32 DMA。静态追踪PC/monitor.py、BSP/Src/runtime.c与board.c，没有发现PC自动重复发送CMD9或固件定时关闭输出的路径。尚无逻辑分析仪TX记录证明是谁触发停流，不能声称已确认意外关闭的底层根因。

确认的软件设计缺陷：CMD_IMU_QUERY原先实际发送GY953自动输出toggle（15/35/45），固件缺少持续读取调度，采集是否继续依赖模块内部输出状态。单纯修改按钮名称不足以建立可靠采集契约。

## 本次行为

- Runtime每20ms排队一次真正的Euler单次查询`A5 95 3A`，不受PC连接、ARM和任务状态影响。不写模块Flash、不复位模块、不改变波特率/输出频率配置。
- 一次Tick最多进行一次周期查询，不追赶错过的周期。每个请求3字节、回应11字节，目标50Hz；实际响应速率须硬件测量。队列发送失败只累计诊断，下个周期继续，不死等。
- 手动CMD9 selector0/1/2改为Acc `A5 C5 6A`、Mag `A5 E5 8A`、Euler `A5 95 3A`单次读取。重复请求仍只是读取，不会关闭持续输出。不新增GUI定时发送线程。
- USART/DMA、GY953解码、运动控制参数、ARM与STOP策略没有变更。自动查询在故障状态仍执行以供诊断，不能清除故障或重新ARM；手动CMD9仍遵循App_Command原有故障拒绝规则。
- Imu_Fresh只由实际收到且通过校验的Euler帧建立。缺回应/坏校验继续呈现过期；不会把排队成功视作新数据。既有IMU失效保护保留。
- 如果模块之前已处于连续输出，新固件不发送toggle去猜测或改变其状态；已有连续帧与查询回应均由原解析器接收。不能因此把Euler序号增长率必然等同于50Hz独立测量频率。

## VS Code诊断

在“STM32Cube 实时监视”添加：

| 表达式 | 含义 |
|---|---|
| `g_imu_query_sent` | Board_Write成功排队的全部读取请求数，通常每秒约50次；不是实际线路发送/响应计数 |
| `g_imu_query_failed` | 发送队列拒绝次数，正常应保持0 |
| `g_imu_last_command` | 最后成功排队的命令，周期Euler为149（0x95） |
| `g_imu_last_query_ms` | 最后成功排队时刻 |
| `g_course.imu.last_byte_ms` | 解析器最近收到字节的时刻 |
| `g_course.imu.euler_seq` | 实际合法Euler帧累计数 |
| `g_course.imu.bad` | 非法帧累计数 |
| `g_runtime_cycles` | 控制任务运行进度 |

请求数增长但字节时刻不变：继续检查物理TX/传感器回应/USART接收；不能认定传感器已响应。字节增长但Euler序号停滞：检查帧类型及坏帧。查询失败持续增长：调查TX队列和中断，不能用提高过期阈值掩盖。

## 验收

用户操作，电机12V断开、ARM0。恢复GY953 TX→PA10、RX←PA9、VCC→原3.3V、GND共地；备用CH340移除。主CH340保持PC UART2接线。

1. 从包根`02-Open-VSCode.cmd`打开`projects/F401_COURSE`，停止旧调试会话，选择Debug生成；启动“STM32Cube: Course ST-Link”，停main后点继续。下载由用户执行，本文不表示已执行。
2. 关闭旧上位机窗口，再打开PC/启动上位机.cmd连接原PC COM。应看到“新版固件自动以50Hz查询Euler”和“读取一次”按钮，无需点击启动。
3. 静置30秒，然后轻转传感器至少3分钟。Euler序号/last_byte_ms应持续变化，IMU age通常小于200ms，无持续递增停更。停止转动时数据帧仍持续到达。
4. 重复点击“读取一次Euler”不应关闭后续采集。保持PWM0、ARM0。本次不把软件测试当成该硬件验收通过。

离线回归运行真实Runtime C代码和受控Board fake，覆盖30分钟模拟时间、无PC采集、缺回应恢复、坏校验、重复读取、TX拒绝、tick回绕和无追赶突发。模拟响应不验证实际GY953、GPIO电平、UART/DMA或实物长期稳定。
